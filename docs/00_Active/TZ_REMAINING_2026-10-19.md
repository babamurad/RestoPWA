## 1. Решения заказчика (без них часть разработки не закрыть)

### R-1. Денежный поток при наличных
**Проблема.** Сейчас в выплатах и аналитике заложена модель «платформа получает деньги и платит ресторанам»: «К выплате ресторану = выручка за блюда − комиссия». При оплате наличными деньги получает курьер, и физический поток другой.

**Варианты:**
- **А.** Курьер сдаёт всю кассу платформе, платформа платит ресторанам (текущая модель). Нужны касса курьера, сверка, регулярные выплаты ресторанам.
- **Б.** Курьер отдаёт ресторану стоимость блюд, а доставку оставляет себе. Ресторан платит платформе комиссию по счёту раз в неделю. Тогда «К выплате ресторану» превращается в «К оплате платформе», нужен реестр долга ресторана.
- **В.** Разные схемы для разных ресторанов.

**Рекомендация:** вариант Б для старта: он совпадает с уже принятым решением «курьер получает всю доставку» и не требует, чтобы платформа держала чужие деньги.

**Влияет на:** D-5, подписи в аналитике, права доступа к реестру расчётов.

### R-2. Где хостится прод
VPS, облако или хостинг-панель? От ответа зависят: нужен ли Docker, как запускать воркеры очередей и Reverb, как делать выкладку и где хранить внешние копии бэкапов. Нужны домен и валидный HTTPS (без него PWA и push не работают) и желательно отдельная тестовая среда (staging).

### R-3. SMS-шлюз
Оператор в стране один (Altyn Asyr / TMCell). Публичного SMS-API для бизнеса не найдено, нужен договор. Пока идут переговоры, можно проверить 1–2 международных агрегатора на доставку SMS на номера +993.
**Состояние в коде:** есть `SendSmsJob` и адаптер `TmSmsService`, но адрес API `https://api.tmsms.tm/v1` — предположение, а не договорённый контракт (см. D-3, п. 5).

### R-4. Юридические тексты
Нужны от юриста: пользовательское соглашение, политика конфиденциальности, публичная оферта — на русском и туркменском. В политике нужен раздел об удалении данных: аккаунт обезличивается (имя, телефон, email, адреса, обращения удаляются; суммы заказов остаются у ресторанов без данных клиента; отзывы остаются анонимными), сотрудники удаляются администратором. Замена текста не требует разработчика: документы лежат в `resources/views/legal/documents/`, версия задаётся в `config/legal.php`.

### R-5. Онлайн-эквайринг
Когда будет договор с банком — подключить провайдера (см. P-4). Код подготовлен: нужен один новый класс шлюза и строка в `PaymentService::GATEWAYS`.

### R-6. Баннер «Скидка 20%» на главной
Сейчас это декоративный баннер без механики скидки: клиент видит обещание, которого нет. Решить: убрать до появления промокодов (P-1) или переписать на нейтральный текст. Правка маленькая (`resources/js/vue/pages/HomePage.vue`, тексты `home.promo.*` в обоих языках).

## 2. Разработка P0 (до запуска)

### D-1. Приложение курьера
**Проблема.** Для курьера есть API (`/api/v1/courier/*`: заказы, предложения, смена статуса, геопозиция, заработок), канал реалтайма `courier.{id}` и автоназначение, но интерфейса нет.

**Что сделать** (раздел PWA для роли `courier`, тот же стек Vue + Pinia + vue-i18n; вход после логина по роли):
1. **Выход на линию:** переключатель «На смене / Не на смене» (`POST /courier/status`). Нельзя выйти из «Занят» при активной доставке.
2. **Предложение заказа:** карточка с рестораном, адресом, суммой доставки, обратным отсчётом (из `expires_at`), кнопки «Принять» (`POST /courier/offers/{id}/accept`) и «Отклонить». Приходит по каналу `courier.{id}` (событие `courier.offer.created`) и по опросу `GET /courier/offers` как запасной путь. По истечении времени карточка пропадает; на 409 — понятное сообщение «Заказ уже взят».
3. **Список доступных заказов** (`GET /courier/orders`): заказы «Готов к выдаче» для ручного принятия.
4. **Текущая доставка:** адрес, телефон клиента (ссылка `tel:`), комментарий, сумма и способ оплаты («взять наличными: X TMT»), кнопки «Забрал у ресторана» и «Доставил» (`POST /courier/orders/{id}/status`).
5. **Геопозиция:** пока есть активная доставка, отправлять координаты раз в 10–15 секунд (`POST /courier/location`); если разрешение не выдано, показать причину.
6. **Заработок:** история доставок и сумма за сегодня, неделю, месяц (`GET /courier/earnings`), статус «ожидает выплаты / выплачено».
7. Язык ru/tk, тёмная тема, работа на слабом интернете (повтор запроса, понятные ошибки).

**Критерии приёмки:**
- [ ] Новое предложение появляется у курьера без перезагрузки; при двух одновременных «Принять» заказ получает только один, второй видит сообщение.
- [ ] Клиент на странице отслеживания видит движение курьера по карте.
- [ ] Курьер не видит чужие заказы и чужой заработок (тест на 403 для других ролей).
- [ ] Vitest на хранилище и компоненты; браузерная проверка полного цикла «предложение → принял → забрал → доставил».

**Зависит от:** Reverb на проде для реального времени (без него работает опрос), D-2 (отмена заказа во время предложения).

### D-2. Отмена и отклонение заказов
**Проблема.** Клиент не может отменить заказ (в API и в приложении нет такой операции). У ресторана нет кнопки «Отклонить» с причиной: статус «Отменён» можно выставить только через форму редактирования. Клиент об отмене не узнаёт (уведомления идут только на «Готовится», «В пути», «Доставлен»), причина нигде не хранится.

**Что сделать:**
1. Поля заказа: `cancelled_by` (клиент / ресторан / админ / система), `cancel_reason` (справочник причин + свободный текст), `cancelled_at`.
2. **Клиент:** `POST /api/v1/orders/{id}/cancel` и кнопка в «Моих заказах», пока заказ в статусе «Новый» или «Подтверждён» (дальше — только через поддержку). Проверка, что заказ его.
3. **Ресторан:** кнопка «Отклонить» на карточке канбана и на странице заказа с обязательной причиной (нет товара, не успеваем, закрываемся и т. д.).
4. Правила состояний: отмена возможна только из разрешённых (`Order::getNextStatuses()`, проверка из D-8); при отмене закрывается ожидающий платёж (`PaymentService::cancelPending`), отменяются активные предложения курьерам, освобождается курьер.
5. **Уведомление клиента** об отмене с причиной (push и SMS через D-3).
6. Аналитика: причины и доля отмен по ресторанам (карточка «Отмены» в аналитике уже есть, добавить разбивку).

**Критерии приёмки:**
- [ ] Клиент отменяет свой заказ в «Новый», в «Готовится» — нет (понятная ошибка); чужой — 403.
- [ ] Отклонённый рестораном заказ: у клиента статус «Отменён» и причина, получено уведомление.
- [ ] Отмена не оставляет «висящих» предложений курьерам и ожидающих платежей.
- [ ] Тесты на каждый переход и на права.

### D-3. Уведомления: email, новый заказ ресторану, недостающие статусы
**Сделано:** push и SMS клиенту, в очереди, на языке клиента. Работают на «В пути» и «Доставлен»; уведомление «Готовится» сейчас практически не срабатывает (см. D-8).

**Что сделать:**
1. **Ресторану о новом заказе:** звуковой сигнал и заметная карточка на канбане; запасной канал — email владельцу (`restaurants.owner_id`), чтобы заказ не пропал, если панель закрыта. Без Reverb канбан не обновляется сам — добавить опрос раз в 20–30 секунд как запасной путь.
2. **Клиенту:** уведомления на «Принят рестораном» и «Отменён» (с причиной из D-2), письмо с чеком, если email указан (Laravel `Notification` с каналом `mail`, шаблоны ru и tk).
3. **Настройки:** оповещения о статусе заказа нельзя отключить, маркетинговые — можно (пока маркетинга нет, достаточно структуры).
4. **Не логировать** телефон и email в открытом виде (использовать `PIIMasker`).
5. **SMS без ложного успеха.** Сейчас при пустых логине и пароле `TmSmsService` «имитирует» отправку и возвращает `true`, и в `sms_logs` появляется статус `sent`. Нужны: флаг `notifications.sms.enabled`, статус `skipped` вместо ложного `sent`, предупреждение при запуске на проде, если SMS включены без учётных данных.

**Критерии приёмки:**
- [ ] Каждый ключевой переход статуса даёт уведомление минимум по одному доступному каналу; сбой одного канала не мешает остальным и не откатывает смену статуса.
- [ ] Включение реального SMS-провайдера — только конфигурация и один класс-адаптер.
- [ ] Тест: смена статуса ставит задачи в очередь (mock), письмо рендерится на двух языках.

### D-4. Защита от перебора и злоупотреблений
**Проблема.** `POST /login` (веб) вообще без ограничения попыток; API-вход и регистрация делят общий лимит 60 запросов в минуту на всю группу `v1`. Один чувствительный путь может «съесть» лимит соседних.

**Что сделать:**
1. Вход: не более 5 попыток в минуту на пару «email + IP», при превышении — блокировка на минуты, понятное сообщение; то же для веб-входа и входа через API.
2. Регистрация: лимит по IP; создание заказа: лимит на пользователя (например, 10 в минуту); `geo/*`: свои лимиты; удаление аккаунта уже ограничено.
3. Отдельные именованные лимитеры в `AppServiceProvider`, а не общий `throttle:60,1`.
4. Ответы 429 на языке пользователя; в Sentry не уходят как ошибки.

**Критерии приёмки:** тесты на 429 для каждого пути; лимит одного пути не влияет на другие; правильные попытки входа не блокируются.

### D-5. Расчёты при наличных (после решения R-1)
Содержание зависит от выбранного варианта; общий минимум:
- **Касса курьера:** сколько наличных принял за смену и сколько должен сдать (по заказам «Доставлен»); сверка и закрытие смены в админке.
- **Реестр расчётов с ресторанами:** при варианте Б — «к оплате платформе» вместо «к выплате ресторану» (подписи в ресторане, админке, аналитике, CSV), отметка получения оплаты; при варианте А — график выплат и подтверждение.
- Заработок курьера уже равен сумме доставки (`courier_earnings`): добавить массовую отметку «выплачено» в админке.
- Тесты на деньги обязательны (правило проекта).

### D-6. Подготовка к выкладке
1. **Чек-лист выкладки** в одном файле: последовательность команд (`migrate`, `queue:restart`, пересборка фронта, `config:cache`), откат, что проверить после.
2. **Runbook инцидентов:** упала очередь, не доходят push, остановился Reverb, не создаётся бэкап, 500 на заказе — куда смотреть и что делать.
3. **Reverb в проде:** инструкция по Nginx/WSS (порт, TLS, заголовки), `BROADCAST_CONNECTION=reverb` и `REVERB_*`, проверка, что значение не осталось `log`. Конфиг supervisor для Reverb уже есть в `deploy/`.
4. **Стратегия сборки фронта.** В репозитории отслеживаются 15 файлов `public/build` (строка в `.gitignore` закомментирована), хотя CI собирает фронт сам. Решить: либо убрать из git и собирать на сервере/в CI, либо коммитить сознательно. Иначе на проде окажется старая сборка без последних изменений.
5. **Автодеплой на staging** (по решению R-2): скрипт или GitHub Actions, который по `main` выкладывает на тестовую среду.
6. **Проверка восстановления бэкапа** на сервере и запись результата в таблицу `OPERATIONS_MONITORING_BACKUPS.md`.

**Критерии приёмки:** выкладка по чек-листу выполняется человеком, который не писал код; на staging проходит полный цикл заказа с реальным WebSocket.

### D-7. Демо-данные: защита и порядок
`DemoDataSeeder` проверен на PostgreSQL (633 заказа, 336 отзывов, 96 отказов, 18 выплат, 6 курьеров, 5 районов, аналитика считается). Замечания:
1. **Нет защиты от продакшена.** Есть только проверка «уже запускали»; при запуске на проде он вызовет `RestaurantSeeder` и создаст демо-пользователей. Добавить отказ при `app()->isProduction()`.
2. **Нет очистки.** Добавить команду удаления демо-данных (все демо-пользователи имеют email вида `demo.*@restopwa.local`, остальное удаляется каскадом), чтобы их не пришлось чистить руками перед выкладкой.
3. **Цены меню Sakura Sushi** дают 98% оборота платформы (см. M-3): график аналитики на демо-данных бесполезен, пока цены не исправлены.
4. Сидер меняет настройки реальных ресторанов (комиссия, цены по районам): указать это в описании сидера.

### D-8. Статусы заказа: единый словарь, проверка переходов, дубли истории
Найдено при составлении этого ТЗ. Влияет на уведомления, отмену (D-2) и страницу отслеживания.

1. **Дубли истории статусов.** Каждое перемещение заказа по канбану пишет в `order_status_history` две одинаковые строки: `OrderService::updateStatus()` создаёт запись вручную, и ту же запись создаёт хук модели `Order` при смене статуса. Клиент видит дубли в таймлайне заказа. Оставить один источник, написать миграцию-чистку уже накопленных дублей (одинаковые `order_id`, `from_status`, `to_status` в пределах секунды).
2. **Три слова для «готовится».** Канбан при перетаскивании в «Готовятся» ставит `confirmed`; система и фабрики используют `preparing`; форма редактирования заказа в Filament предлагает устаревший `cooking` и не содержит `preparing`. Уведомление «Заказ начали готовить» привязано к `cooking`, поэтому не срабатывает ни от канбана, ни от системы. Привести к одному словарю: `pending → confirmed → preparing → ready_for_pickup → delivering → delivered` (+ `completed` для самовывоза, `cancelled`); миграция данных `cooking → preparing`; форма Filament берёт список из `Order::STATUSES`. Решить, нужен ли ресторану отдельный шаг «Принят»: если да, то перетаскивание в «Готовятся» ставит `preparing`, а `confirmed` — явное действие «Принять» с уведомлением клиенту (D-3).
3. **Переходы не проверяются.** Правила описаны в `Order::getNextStatuses()` и применяются только в API курьера. Канбан и форма в Filament позволяют поставить любой статус, в том числе вернуть доставленный заказ в «Новый» (при этом комиссия и заработок курьера уже начислены). Применять `getNextStatuses()` на канбане и в форме; для админа оставить исключение с записью в историю (`changed_by`, причина).

**Критерии приёмки:**
- [ ] Один перенос по канбану даёт одну запись истории; в существующих данных дубли удалены.

## 4. Ручные действия (не код)

### M-1. Защита ветки `main`
Сейчас в `main` можно писать напрямую, минуя CI (последний коммит `Create DemoDataSeeder.php` сделан именно так). GitHub → репозиторий → **Settings → Branches → Add branch ruleset** (или Branch protection rule) для `main`:
1. **Require a pull request before merging.**
2. **Require status checks to pass:** добавить `Backend (Pint + PHPUnit)` и `Frontend (Vitest + build)`.
3. **Require branches to be up to date before merging.**
4. Не разрешать обход правил администраторам (Do not allow bypassing) — иначе защита не работает для владельца.
5. По желанию: Block force pushes и Restrict deletions.

Названия проверок должны совпадать с названием задач в `.github/workflows/ci.yml`.

### M-2. Выкладка на сервер
Пошагово в `OPERATIONS_QUEUES.md` и `OPERATIONS_MONITORING_BACKUPS.md`. Коротко:
1. `composer install`, `npm ci && npm run build`, `php artisan migrate`.
2. `.env`: `QUEUE_CONNECTION=database`, ключи Sentry, `BACKUP_ARCHIVE_PASSWORD`, `BACKUP_NOTIFICATION_EMAIL`, `BACKUP_DISKS=backups,s3`, `BROADCAST_CONNECTION=reverb`.
3. Supervisor (`deploy/supervisor/`) и cron (`deploy/cron/`).
4. Установить `mysqldump` или `pg_dump`, запустить `php artisan backup:run`, затем пробное восстановление.
5. Разовые команды, каждую сначала с `--dry-run`: `orders:recalculate-commission`, `orders:fix-legacy-delivery-fee`.
6. После каждого следующего обновления: `php artisan queue:restart`.

### M-3. Исправление цен меню (в данных, не в коде)
В вашей локальной базе: «Филадельфия» = 5 999,99 TMT (в базе 599999 тыйн), «Калифорния» = 549 TMT, «Сет „Сакура“» = 249 TMT, «Мисо суп» = 19,90 TMT; у остальных ресторанов блюда стоят 2–7,5 TMT. Похоже на опечатку или не тот масштаб. Проверить цены в админке; на проде — до запуска.

## 6. Критерии готовности к запуску

- [ ] Полный цикл на staging: клиент оформляет заказ → ресторан принимает → курьер получает предложение и доставляет → клиент видит движение курьера → получает уведомления → оставляет отзыв.
- [ ] Клиент и ресторан могут отменить заказ, клиент узнаёт об этом.
- [ ] Решён вопрос с деньгами при наличных (R-1), реестр расчётов работает.
- [ ] Reverb, очереди, бэкапы, Sentry подняты и проверены (в том числе восстановление из бэкапа).
- [ ] Включена защита ветки `main`; CI блокирует мерж при красных тестах.
- [ ] Юридические тексты на двух языках размещены, регистрация без согласия невозможна.
- [ ] Выкладку и откат по чек-листу выполнил человек, не писавший код.

**Сквозные правила** (из роадмапа, раздел 7): любой PR по деньгам и статусу заказа — с тестом; у каждого нового эндпоинта явная проверка роли и тест на 403; логи с персональными данными — через `PIIMasker`; денежные поля — через `MoneyCast`; при изменении данных заказа обновлять `order_contract.md`.
